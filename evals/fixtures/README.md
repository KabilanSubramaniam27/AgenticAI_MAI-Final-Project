# TripRadar EDD fixtures

**Version 1.0-draft; pending user review.** These files provide structured inputs for all 80 existing Golden Dataset V1 cases. They do not execute agents or establish a passing agent baseline.

## Separation from destination knowledge

Everything here lives under `evals/fixtures/`. Synthetic records must never be ingested into the destination Chroma collection or displayed as actual travel recommendations. This fixture creation did not access Chroma, call providers, generate embeddings or alter either local or Cloud indexes. The existing `guides/passages.json` retains four real archived, attributed Wikivoyage passages; those are distinct from the explicitly fictional passages in case files.

## Layout and loading contract

- `index.json` maps each stable golden case ID to `cases/<case_id>.json`.
- Each case contains the fixed evaluation clock, user input, agent target, `input_refs`, deliberately invalid conditions, and expected results for the grader.
- Paths in `input_refs` are relative to `evals/fixtures/`. Resolve them locally before giving the agent its task. Supply only `user_input`, clock and referenced inputs; **never supply `expected`, `expected_behavior`, `success_criteria`, or `failure_edge_cases` as agent inputs**.
- `trips/` contains resolved, partial, or deliberately invalid trip state. Unused fields in shared trip templates are not permission to invent evidence. For weather/itinerary-only tasks, occupancy, airfare dates and lodging fields are outside the specialist's task; consume the task-specific dates and fields.
- `flights/` and `hotels/` contain normalized synthetic provider-boundary responses with explicit price basis, occupancy, dates, tax inclusion, validity, and errors.
- `weather/` contains fixed daily forecasts and explicit policy thresholds; `specialist_results/` supplies matching activities/version. Historical, missing, stale and malformed forecasts are deliberate cases.
- `currency/` contains exact synthetic rates or unavailable/not-required states. Rates use source-to-target direction. Money and rates are decimal strings.
- `specialist_results/` contains orchestration inputs, cost-evidence ledgers, prior state, revisions and fictional cited itineraries. These are independent synthetic inputs, not output generated by an implemented specialist.
- `guides/TR-ITIN-*.json` selects aliases from `guides/passages.json` or embeds fictional guide facts for controlled behavior tests. Fixture aliases resolve locally; they are not external citations. Duplicate and conflicting passages are intentional in their designated case.
- `versions/before-fixtures-1.0/` preserves the previous golden companion metadata and manifest before the structured links were added. Original CSV labels are unchanged.

All new travel offers, forecasts, rates, ledger evidence and invented venue facts are synthetic. Some cases deliberately include `environment=test` inside a synthetic response to test correct labeling. This is not a recorded Amadeus response or proof of test API compatibility. Do not use real API keys, payment data, reservations or private user data in fixtures.

## Integration boundary and limitations

These are normalized domain responses, not raw Amadeus/Open-Meteo/Frankfurter HTTP wire formats. A future fixture adapter should map each input to its corresponding tool contract; live provider parsing needs separate contract tests and permitted recorded responses when implemented. A `refresh_result` represents the response after an expired quote; `attempts_exhausted` represents final failure, not a detailed retry-event sequence. V2 can add call ordering and retry assertions.

Unknown values are JSON null, not zero. Error states distinguish unavailable, no results and not requested. Fixtures containing invalid dates or out-of-range numbers deliberately test rejection and must not be “cleaned” into valid input. Fixed `as_of` values govern validity; the real current date is irrelevant during replay.

The synthetic repeated-walk itinerary exists to isolate orchestrator reconciliation/date checks; it is not a gold example of ten-day itinerary quality. Actual recommendation quality and live retrieval need separate reviewed cases. Scope is the four requested agent suites, not the deferred end-to-end suite.

## Validation and review

Run from the project root:

```bash
.venv/bin/python evals/validate_fixtures.py
```

The validator uses local files and standard-library calculations. It checks 80 case links, 20-per-agent counts, preservation of golden labels, reference resolution, checksums, price/tax/night arithmetic, budget/FX arithmetic, forecast/date/threshold outcomes, invalid-input cases, and synthetic itinerary evidence links. It does not call an LLM or evaluate prose quality, all provider field eligibility rules, or actual SDK/API schema compatibility.

Review the fixture inputs and expected results alongside the CSV labels before freezing either version. Approved changes require new fixture/dataset metadata and refreshed checksums. Execution outputs should go under ignored `data/runtime/evals/`, not into the golden answer key. Retain old versions when results have been recorded against them.
